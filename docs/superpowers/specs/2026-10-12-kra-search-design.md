## 1. 목적

대한민국 공공기관 직원이 **자기 PC 안의 업무 문서를 내용과 의미로 찾는** Windows용 로컬 검색 프로그램을 만든다. Google AI Edge Foresight처럼 모든 처리를 PC 안에서 하고, 공공기관 환경(HWP 중심, 망분리, 다양한 사양의 PC, 개인정보·보안 요구)에 맞춘다.

**핵심 가치**: "파일 이름은 모르지만 내용은 대충 기억나는" 문서를 1초 안에 찾는다.

**우선순위**: 모든 처리가 로컬이므로 **검색 품질 · 성능 · 속도를 최우선**으로 한다. 동시에 **컴퓨터에 익숙하지 않은 사람도 그냥 쓸 수 있어야 한다**(§3.3).

### 1.1 Everything과의 관계
| 상황 | 더 나은 도구 |
|---|---|
| 파일 이름을 알고 위치만 모를 때 | Everything과 동등 수준을 목표로 함 (M6 파일명 엔진) |
| 내용·의미로 찾을 때 (HWP/PDF/Office 본문, 약어, 공문 필터, 버전 정리, 개인정보 점검) | kra-search |

## 2. 사용자 · 환경 가정

**사용자가 정한 것**
- Windows PC, 무설치 실행 또는 단일 설치파일.
- PC 사양: **대체로 i5 이상**, 일부 저사양, 일부 RAM 16GB. 성능을 위해 Rust.
- HWP가 가장 많이 쓰이는 형식.
- 임베딩 모델: **EmbeddingGemma 2 고정**(다른 모델과 비교·교체 검토하지 않음. 사용자 교체 기능은 제공).
- 공유 드라이브·USB 사용이 제한적 → **로컬 디스크가 핵심**.
- 문서중앙화 문서는 로컬에서 접근 불가 → 보류.
- Fasoo DRM은 대외용 위주로 일부 파일에만 적용.
- 관리자 권한 확보는 어렵지 않음. 대상 기관(한국마사회) 업무 PC 는 **Windows 10 Pro**(2026-10-14 폐쇄망 진단으로 확인, 처음엔 Enterprise 로 알고 있었음). EFS 는 Pro 에서도 지원(진단: 볼륨 지원·정책 허용) — Enterprise 전용 기능에 기대지 않는다.
- 다른 공공기관과 공유할 가능성 있음 → 기관별 정책 파일, **오픈소스 라이선스 준수**(상용 라이선스 키·과금 기능은 없음).
- 개발 PC는 macOS, 테스트는 GitHub Actions + 사내 폐쇄망 Windows PC.

**설계상 가정**
- 망분리 환경: 실행 중 **외부 네트워크 호출 0**. 모델 등 모든 리소스 내장.
- 기준 PC
  - **주 기준(보통)**: i5 8세대 4코어, RAM 8GB, SSD, Windows 10/11. 합격선(§13)은 이 PC 기준.
  - **최소 지원(저사양)**: 2코어/4스레드 i3·셀러론 7세대, RAM 4GB, SATA SSD, Windows 10. 완화된 합격선 적용.
  - GPU는 사용하지 않음(CPU 추론).
- 한 PC는 대부분 1인 1대. 여러 사용자가 쓰는 경우에도 내용 색인은 사용자별.

## 3. 범위

### 3.1 1차 범위
1. 문서 내용 검색: **키워드(BM25) + 의미(임베딩) 하이브리드**.
2. 지원 형식(내용 추출): HWP, HWPX, PDF, DOCX, XLSX, PPTX, **ODT/ODS/ODP**, TXT/CSV.
   - 배포용 HWP 복호화 지원. 암호 문서·DRM·추출 실패 파일은 파일명·메타데이터만 색인.
3. 파일명 검색: 색인 대상 문서 + (설치판, M6 이후) **로컬 NTFS 전체 파일명**(MFT/USN 기반 서비스). M6 이전에는 색인된 문서 목록에서만 파일명 검색.
4. 의미 검색 2단계 범위: **빠른 의미 검색(문서 카드)** → **정밀 의미 검색(본문 청크)** (§6.2).
5. 공공기관 특화: 공문서 구조 인식, 약어·동의어 사전, 파일 버전 묶기, 개인정보 탐지·점검.
6. 상주형(트레이 + 전역 단축키) 기본, 설정에서 끌 수 있음.
7. 모델 관리: 기본 EmbeddingGemma 2 내장, 다른 GGUF 임베딩 모델로 교체 가능.
8. 배포: MSI(기본, 서비스 포함) + 무설치 zip(기능 축소).
9. 진단·평가 도구: `--diagnose`, `--eval`.

### 3.2 1차 비범위 (로드맵 §16)
LLM 요약·질의응답, 붙임 파일 연결, 네트워크 경로, 이미지·스캔 PDF 검색, 이름·주소 개인정보 탐지, 재순위 모델, 옛 Office 형식, 한셀/한쇼, 문서중앙화·Fasoo SDK 연동, GPU 가속, KCMVP 검증 암호모듈.

### 3.3 사용성 원칙 (모든 설계에 우선 적용)
1. **아이콘 하나**: 사용자는 시작 메뉴/바탕화면의 `KRA 문서검색` 하나만 안다. 워커는 앱이 자동으로 띄우고 끄며, 서비스는 설치 시 자동 등록, 로그인 시 자동 시작.
2. **여는 방법 여러 개**: 단축키(`Alt+Space`), **트레이 아이콘 클릭**, 시작 메뉴 아이콘 — 어느 것이든 검색창이 열린다.
3. **알아서 복구**: 워커·서비스 비정상 종료, 암호 키 분실, 색인 손상은 자동 재시작·재색인으로 처리. 사용자에게 오류 대화상자를 띄우지 않고 색인 현황에만 기록.
4. **쉬운 말**: 화면에 "임베딩·청크·EFS·BM25" 같은 기술 용어를 쓰지 않는다(용어 대응표는 UI D7). 기술 정보는 "자세히" 아래에만.
5. **설정 없이 동작**: 첫 실행에서 `색인 시작` 한 번이면 끝. 모든 설정은 합리적 기본값을 갖는다.

## 5. 아키텍처

### 5.1 프로세스 구성과 역할
```
[kra-search-svc]  Windows 서비스, SYSTEM, 설치판만
   MFT 열거 + USN 저널 구독 → 파일명 색인(메모리) · 변경 이벤트
   ↑↓ named pipe (보안 규칙 §7.6)
[kra-search.exe]  사용자 권한, 상주 — "앱"
   트레이 · 전역 단축키 · 작업 대기열 · 검색
   ★ 임베딩(낮은 우선순위 스레드 풀)  ★ 모든 색인의 유일한 쓰기 주체
   모델: 한 벌만 로드. 검색 단축키 누르는 순간 미리 로드 시작, 5분 미사용 + 색인 없음 → 해제
   WebView2 창: 열 때 생성, 닫은 뒤 10분 숨김 유지 후 해제
   ↑↓ 로컬 파이프
[kra-search.exe --worker]  사용자 권한, 색인할 때만 — "워커"
   ★ 추출만: 파일 → Document(+공문 메타, 개인정보 치환 완료 텍스트, SimHash) 를 앱으로 전송
   비정상 종료·멈춤 격리용. 앱이 자동 실행/종료/재시작
```
- **사용자가 직접 실행하는 프로세스는 앱 하나뿐**(§3.3). 워커·서비스는 자동 관리.
- **쓰기 주체는 앱 하나**: tantivy·벡터·meta.db 쓰기는 앱만 한다. 워커는 결과를 파이프로 보낼 뿐 → 워커가 죽어도 색인 정합성에 영향 없음.
- **파일당 제한 시간**: 워커의 CPU 시간 기준 30초(기본). 초과 시 앱이 워커 프로세스를 종료하고 해당 파일을 "시간 초과"로 기록 후 워커 재시작. (Rust 스레드는 네이티브 호출 중 중단 불가하므로 프로세스 종료로만 보장)
- **우선순위**: 워커는 백그라운드 모드(CPU·I/O 우선순위 낮춤). 앱의 임베딩 스레드는 **CPU 우선순위만 낮추고 메모리 우선순위는 정상**(모델 페이지가 먼저 밀려나 처리량이 붕괴하는 것 방지). Windows 11에서는 EcoQoS 추가 적용.
- **문서 본문은 SYSTEM 권한으로 읽지 않는다.** 내용 색인은 사용자 권한 워커만 수행 → 파일 ACL이 자연스럽게 지켜짐.
- 서비스가 없을 때(무설치판·설치 차단): 지정 폴더 `ReadDirectoryChangesW` 감시 + 시작 시 mtime/크기 비교 스캔.
- 자동 시작: 설치판은 **HKLM Run**(모든 사용자) + 사용자별 끄기 설정. 무설치판은 HKCU Run(설정에서 켤 때만).

### 5.2 Rust 워크스페이스 모듈
| 크레이트 | 책임 | macOS |
|---|---|---|
| `extract` | 파일 → `Document{title, blocks[], gongmun?, flags}`. 형식별 추출, DRM/암호 감지, PDF ToUnicode 검사 | ✔ |
| `gongmun` | 블록에서 공문 메타(제목·문서번호·시행일·수신·발신·붙임 목록) 추출 | ✔ |
| `pii` | 식별번호 탐지, 유형 자리표시자 치환, HMAC | ✔ |
| `llama-sys` | llama.cpp 고정 버전 + bindgen 바인딩(임베딩 API만) | ✔ |
| `embed` | 모델 프로필, 문서 카드 생성, 청크 분할, 접두어, MRL 축소·정규화·양자화 | ✔ |
| `index` | tantivy 스키마·토크나이저, SQLCipher, 하이브리드 검색, 버전 묶기 (벡터는 vector 크레이트) | ✔ |
| `vector` | 벡터 연산(MRL 축소·정규화·int8·이진)·평면 저장소 — 의존성 없음(KI-008) | ✔ |
| `query` | 검색어 해석(날짜 표현, 번호 형식, 약어 확장, 검색어 유형 분류) | ✔ |
| `lexicon` | 약어·동의어 사전(내장 + 기관 TSV) | ✔ |
| `crawler` | 스캔·감시·대기열·우선순위·공정 스케줄링 | ✔(스텁 감시) |
| `platform` | Windows 전용: USN/MFT, EFS, DPAPI, 서비스, 단축키, 우선순위, 유휴 감지, WER 제외, DLL 경로 보안. **macOS용 스텁 제공** | 스텁 |
| `app` | Tauri 셸, 트레이, 창 관리, IPC, 설정, 진단·평가 명령 | ✔ |
| `svc` | 파일명 엔진 서비스 | ✘ (Windows 전용) |

각 크레이트는 다른 크레이트 내부를 몰라도 단독 테스트 가능해야 한다.

### 5.3 데이터 위치
`%LOCALAPPDATA%\KraSearch\` (사용자별, 설치판·무설치판 공통)
- `data\` ← **이 폴더 전체에 EFS 적용**(가능한 경우)
  - `tantivy\` — 키워드 색인
  - `vectors\<임베딩 지문>\cards.<세대>.vec`, `chunks.<세대>.vec` — 문서 카드·본문 청크 벡터(int8, 이진). 삭제 기준은 meta.db(가리키지 않는 슬롯 = 삭제), 압축은 새 세대 파일로(DEC-048)
  - `meta.db` — SQLCipher (파일·내용·청크 텍스트(개인정보 치환 후)·상태·공문 메타·개인정보 개수·HMAC·SimHash)
  - `webview\` — WebView2 사용자 데이터 폴더(캐시·저장소)
  - `logs\`
- `keys\` — DPAPI로 보호된 SQLCipher 키·HMAC 키
- 무설치판도 같은 위치(exe 옆에 쓰지 않음 — 권한·EFS 일관성).
- **키를 풀 수 없으면**(로컬 계정 비밀번호 관리자 재설정, 프로필 재구성 등) `data\`를 지우고 자동 재색인(§3.3).

## 6. 색인 파이프라인

### 6.1 흐름
```
변경 감지 → 작업 대기열(meta.db) → 워커: 추출 → 공문 인식 → 개인정보 치환 → SimHash → 앱으로 전송
→ 앱: 키워드 색인 → (유휴 시) 문서 카드 임베딩 → (유휴 시) 본문 청크 임베딩 → 커밋
```

### 6.2 3단계 색인 (사용자 표시 이름)
| 단계 | 내용 | 비용(M0 측정 — 폐쇄망 i7-13700, Q8, 문서 1만 개) | 화면 표시 |
|---|---|---|---|
| 1. 키워드 | 추출 + 파일명/키워드 색인 + SimHash | 수십 분 | "키워드 검색" |
| 2. 문서 카드 | 문서당 벡터 1개. 입력 = 제목(공문 제목 우선) + 공문 메타 + 목차·소제목 + 첫 문단, **≤ 256토큰**. 순서: **최근 수정 문서·문서 형식(HWP·PDF·Office·ODF) 먼저**, 데이터 형식(TXT·CSV·시트)은 뒤(결정 #27) | **약 33.5분**(m1-diag-2 실측: 실제 카드 평균 123토큰 × Q8 612토큰/초). M0 의 21분은 평가 문서 카드(평균 64)로 낸 값이었다. 주 기준 i5 는 미측정 — 더 느림 | "빠른 의미 검색" |
| 3. 본문 청크 | 문서 본문 청크 벡터. 우선순위: **최근 수정·최근 열람 문서 → 나머지 최신순** | 문서당 청크 p50 7 · p90 63(폐쇄망 HWP). 510토큰/초면 청크 300토큰 1만 개당 약 1.6시간 — 수십만 청크면 수일 유휴 시간 | "정밀 의미 검색 N%" |
- 2·3단계는 PC 유휴 시(기본: 입력 없음 2분) 진행. 고성능 프로필은 사용 중에도 1스레드 허용(§10.2). M2(명령줄)는 `index` 명령 안에서 키워드 → 카드 → 본문 순으로 끝까지 돌고, 유휴 실행은 M5 에서 붙인다(DEC-046).
- 3단계 처리 순서는 §6.6 "본문 3단 순서".
- 2단계가 끝나면 모든 문서가 의미로 검색된다. 3단계가 된 문서는 정확한 구절까지 찾는다.

### 6.3 범위 · 제외
- 설치판 기본: **모든 로컬 NTFS 드라이브**의 대상 확장자.
- 무설치판 기본: 문서·바탕화면·다운로드 + 사용자 추가 폴더.
- 기본 제외: `Windows`, `Program Files*`, `AppData`, `$Recycle.Bin`, 임시 폴더, 한글 자동저장/백업(`.asv`, `.bak`), Office 임시(`~$*`). 사용자 편집 가능.

### 6.4 중복 제거
- 파일 내용 해시(xxh3-128) 기준으로 추출·임베딩은 한 번, 경로는 여러 개 연결.

### 6.5 추출
- 출력: `Document { title, blocks: [Block{kind: Heading|Paragraph|TableHeader|TableRow|Note, text, loc: 쪽/구역/표}], gongmun: Option<GongmunMeta>, flags: {drm, encrypted, distribution, truncated, no_text_layer} }`.
- HWP: rhwp. 배포용 문서는 rhwp 복호화 사용. 암호 문서는 감지만.
- DRM: Fasoo 등 알려진 헤더 시그니처로 감지 → 🔒. **복호화 플러그인 인터페이스**(`trait Decryptor`)만 정의, 구현 없음.
- PDF: ToUnicode 매핑이 없어 글자가 깨지는 PDF를 감지하면 `no_text_layer`로 표시하고 파일명만 색인.
- 파일 크기 100MB 초과: 내용 추출 생략.
- TXT/CSV: UTF-8/CP949 자동 판별.

### 6.6 청크 분할 (3단계용)
- 구조 기반: 제목·문단 경계 존중. 표는 행을 `열이름: 값` 형태로 직렬화하되 **여러 행을 목표 크기까지 묶고, 청크마다 표 머리글(TableHeader)을 반복**한다. rhwp `rag::build_chunks`의 방식을 참고·재사용 검토.
- 목표 크기 **300토큰**(최대 400). M0: 300·400 동률(차이 잡음 수준), 500은 일관되게 낮음 → 동률이면 작은 쪽.
- 입력 형식은 모델 프로필이 정의. EmbeddingGemma 2: 문서 `title: {공문제목|파일명} | text: {청크}`, 검색어 `task: search result | query: {검색어}`.
- **문서당 본문 청크 상한** (초과분은 키워드 색인만):
  - 본문 문서(HWP/HWPX/PDF/DOCX/PPTX/ODT/ODP/TXT): 안전장치 **2,000청크**(약 700~1,000쪽).
  - 표 데이터(XLSX/ODS/CSV): **200청크**.
- M0 측정: 한글 1,000자 ≈ **630토큰**(폐쇄망 HWP 539개 중앙값 627, 공개 문서 649) → A4 1쪽(1,000~1,500자) ≈ 630~950토큰 ≈ 청크 2~3개.
- **공정 스케줄링**: 큰 문서는 50청크 단위 조각으로 나눠 여러 문서를 번갈아 처리. 큰 문서는 **목차·소제목 포함 청크를 먼저** 임베딩.
- **본문 3단 순서** (2026-10-15 사용자 결정 #28 — 데이터 형식이 본문 토큰의 68%, m1-diag-2):
  1. 문서 형식(HWP·HWPX·PDF·DOCX·PPTX·ODT·ODP) 본문 전체, 최근 수정 먼저.
  2. 데이터 형식(TXT·CSV·XLSX·ODS) 문서당 **앞 20청크**.
  3. 데이터 형식의 나머지, 위 상한까지 — PC 를 쓰지 않을 때 계속. **설정으로 끌 수 있고 기본 켬**(저사양 프로필 기본 끔, §10.2). 화면의 "정밀 의미 검색 N%"는 1·2만 센다(UI D5 ④·⑥).

### 6.7 임베딩 (llama.cpp 설정)
- 풀링: **평균(mean) 풀링 강제**. 모델 그래프가 토큰별 512→768 투영 후 평균하므로 참조 구현과 수학적으로 동일.
- 양방향 어텐션 → 입력 하나가 한 마이크로배치에 들어가야 함: `n_ubatch = n_batch ≥ 최장 입력(청크 + 접두어)`.
- 출력은 정규화되지 않음 → **MRL 차원 축소(768→512, M0 확정) 후 직접 L2 정규화** → int8 스칼라 양자화 + 이진 부호 비트(원본 768차원에서). M0: 512 0.9140 · 768 0.9132 · 256 0.9038(Q8·청크 400).
- 양자화 수준: **Q8_0**(M0 확정, 2026-10-14 사용자 승인). nDCG@10 Q8이 1.28%p 높고(512차원), 마사회 문서 질의는 세 유형 모두 Q8이 앞섬. 대가: 폐쇄망 i7 에서 Q4 보다 1.8배 느림(510 vs 940토큰/초). FP16은 이 모델에서 문제가 보고되어 사용하지 않음.
- **M0 필수 검사**: GGUF 출력 vs 원본(sentence-transformers) 출력 코사인 일치도.
- 빌드: `GGML_BACKEND_DL` + `GGML_CPU_ALL_VARIANTS`(CPU별 `ggml-*.dll` 동봉, 런타임 선택), `LLAMA_STATIC_CRT=1`, OpenMP 끔, `LLAMA_CURL` 끔.

### 6.8 저장 · 일관성
- meta.db가 기준. 앱이 tantivy·벡터를 배치 커밋 후 커밋 번호를 meta.db에 기록. 재시작 시 커밋 번호로 정합성 복구.
- 벡터 파일은 추가 전용 + 삭제 표시. 삭제 비율이 높아지면 유휴 시 압축.
- 색인 스키마 버전 불일치 시 자동 재색인 + 안내.

### 6.9 실패 처리
- 시간 초과, 손상, 암호, 텍스트 없음, 100MB 초과 → 상태 기록 + 파일명만 색인. **수정 시각이 바뀌면 1회 재시도.**

## 7. 보안 · 개인정보

### 7.1 보호 계층과 보안성 검토 논리
1. **식별번호 비저장(핵심)**: 주민·외국인등록번호 등 식별번호의 **숫자는 색인·DB·로그·화면 어디에도 저장하지 않는다**(§7.2). 따라서 고유식별정보 암호화 의무의 대상 데이터가 존재하지 않는다.
2. **EFS**: `data\` 폴더 전체(키워드 색인, 벡터, DB, WebView2 데이터, 로그). 불가(Home 에디션, 정책 차단) 시 기본은 **경고 후 계속 사용**, 기관 정책 `require_efs = true`이면 색인 거부.
3. **SQLCipher**: meta.db 추가 암호화(키는 DPAPI CurrentUser).
- **KCMVP**: SQLCipher(AES)·EFS는 KCMVP 검증 모듈이 아니다. 보안성 검토 자료에는 1번을 보호 근거로 하고, 2·3번은 **추가 방어층**으로 기술한다. 검증 모듈 요구 기관이 생기면 로드맵에서 대응.
- EFS 미적용 PC에서는 키워드 색인·벡터가 평문(본문 단어·이름 복원 가능)임을 검토 자료에 **수용 위험**으로 명시.

### 7.2 개인정보 탐지 (1차)
- 대상: 주민등록번호, 외국인등록번호, 여권번호, 운전면허번호, 계좌번호, 휴대폰번호, 이메일.
- 주민·외국인등록번호의 검증 숫자는 **확신도 가산 요소**로만 사용(2020-10 이후 부여 번호는 검증 숫자가 맞지 않을 수 있어 필터로 쓰지 않음).
- 처리: 워커에서 탐지 즉시 텍스트를 `⟨주민번호⟩` 같은 **유형 자리표시자로 치환**. 이후 모든 저장(키워드 색인, 청크 텍스트, 임베딩 입력)은 치환된 텍스트만 사용.
- 문서별 유형별 개수 저장.
- **번호로 검색**: 정규화 후 **HMAC-SHA256(DPAPI 보호 키)** 값만 색인 → 검색어가 번호 형식이면 정확 일치 검색. 부분 번호 검색 불가. 이 값은 같은 사용자 키로 대입 공격이 가능하므로 "익명"이 아니라 **가명 처리**로 기술.
- **파일명**도 탐지: 파일명에 식별번호가 있으면 문서에 🛡 표시, 키워드 색인의 파일명 필드에는 치환된 이름을 넣는다. 실제 경로는 파일을 열기 위해 meta.db(암호화)에만 저장.
- **이름은 색인함**(이름으로 검색 가능). 이름·주소만 있는 문서는 1차에서 탐지하지 않음(로드맵).

### 7.6 권한 · 프로세스 보안
- 앱·워커: 사용자 권한. 서비스: SYSTEM(파일명 메타데이터만).
- **서비스 파이프**
  - `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`, DACL = SYSTEM + INTERACTIVE.
  - 요청마다 `ImpersonateNamedPipeClient`로 호출자 토큰 확보 → 결과마다 **상위 폴더 `FILE_LIST_DIRECTORY` 권한**을 AccessCheck로 확인한 것만 반환.
  - **변경 이벤트도 연결된 사용자별로 같은 방식으로 필터링**.
  - 클라이언트(앱)는 `SECURITY_SQOS_PRESENT|SECURITY_IDENTIFICATION`으로 연결하고 `GetNamedPipeServerProcessId`로 서버가 진짜 서비스인지 확인(위장 파이프 방지).

- **DLL 로드**: 프로세스 시작 직후 `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR)`. ggml 백엔드·pdfium은 exe 폴더의 **절대 경로**로만 로드. 동봉 DLL은 모두 서명.
- **사용자 추가 GGUF**는 신뢰할 수 없는 입력으로 취급. 기관 정책 `model.allow_custom = false`로 차단 가능.

## 8. 검색 · 순위

### 8.1 검색어 해석
- 날짜 표현("작년", "지난달", "2024년 상반기") → 📅 칩. **필터가 아닌 순위 가산**, 칩 ✕로 해제.
  - **인식 범위는 내장 데이터 표**(M2 설계 §4.1): 해·반기·분기·달·주·날·계절·막연한 기간, 한자어(금년·전년도·객년·금월·금일)·구어(저번 달·요새·엊그제)·약식('25, 25.9월, 3/4분기, 3Q) 포함. 기관 사전 TSV 와 같은 형식으로 바깥 파일을 덧붙일 수 있다(연결은 M5). 업무 고유 표현(경마 주차·회차)은 실사용 피드백으로 더한다(§16).
  - **미래 표현(내년·명년·익년·차년도·다음 달)은 칩으로 만들지 않고 검색어에 남긴다** — "내년 계획"은 올해 쓴 문서.
  - 연도 없는 달은 기준 시점에서 가장 가까운 지난 그 달. 막연한 표현(최근·요즘·얼마 전)은 기간을 넓게, 가산을 약하게.
  - **기준 시점**: 검색하는 순간의 PC 날짜. "작년"은 기준 시점의 전년 1~12월(회계연도 = 역년).
  - **문서 날짜**: 공문 시행일(M4~) → 없으면 파일 수정일. 수정일은 메일 저장·다시 저장으로 실제 작성일과 다를 수 있으므로 시행일이 있으면 항상 우선.
    - M2: 1년 이상인 칩(작년·올해·2025년)은 **제목·파일 이름에 적힌 연도**가 파일 날짜보다 우선(사용자 요구 2026-10-15, DEC-062). 연도 없는 시기(연말·3분기)는 해마다 되풀이되는 기간(DEC-063).
  - **칩으로 바꾼 표현은 키워드·의미 검색어에서 뺀다**(본문에 "작년"이라는 글자가 있는 문서가 올라오는 것 방지). 칩 ✕로 해제하면 원래 검색어 그대로 검색. 단 "올해 3분기까지 수출 실적"처럼 날짜가 **본문 내용**인 질의에서 키워드를 잃을 수 있어, 표현 종류별로 뺄지를 M2 평가(`temporal` 질의 회귀)로 정한다.
  - 기준 시점은 바깥에서 주입한다(테스트·`--eval`에서 고정 날짜 사용 → 해가 바뀌어도 결과 재현).
- 번호 형식 → HMAC 정확 일치 경로.
- 약어·동의어 확장: 원래 단어보다 낮은 가중치로 OR. 검색 시점 적용(사전 변경 시 재색인 불필요). 내장 사전(중앙행정기관 약어) + 기관 TSV(가져오기/내보내기).
- **검색어 유형 분류**: 짧은 명사(2~3글자)·문서번호·사람 이름·파일명 형태 → "키워드형", 문장형 → "의미형". 결합 가중치에 사용(§8.3). M2: 사람마다 검색 습관이 달라 **기본은 나누지 않는다**(나누는 쪽이 평가에서 이기지 못함, DEC-058·DEC-064).

### 8.2 검색 경로
| 경로 | 방식 |
|---|---|
| 파일명 | 서비스(전체 디스크, M6~) + 색인 문서 목록 |
| 키워드 | tantivy BM25. 필드 가중치: 공문 제목 > 파일명·문서 제목 > 소제목 > 본문. 본문은 **형태소 필드(품사 필터) + 한글 bigram 필드**(위치 기록, 다글자 단어는 bigram 구절 일치) |
| 의미 | 검색어 임베딩 → (a) 문서 카드 벡터 전체 스캔(int8) + (b) 본문 청크: **768비트 이진 코드 해밍 거리**로 후보 **max(1,000, 청크 수 × 2%)**개 → int8 재계산 → 상위 200 |
- M0 측정: 상위 10 재현율 해밍256@5% 0.952 · 해밍768@2% 0.957. 비대칭 점수는 스캔이 수십 배 느려 채택 안 함(폐쇄망 50만 개: 해밍768 6ms · 비대칭256 488ms · int8 정밀 48ms). 평면 스캔으로 충분 — HNSW 불필요.

### 8.3 결합 · 순위
- 문서 단위 **가중 RRF**. k와 경로별 가중치는 `--eval`로 조정(초기 k=60, 탐색 범위 10~60).
- **검색어 유형별 가중치**: 키워드형은 키워드 경로 우선, 의미형은 의미 경로 비중 확대.
- **유사도 하한**: 코사인이 하한 미만인 의미 결과는 결합에서 제외(관련 없는 최근접 결과가 강한 키워드 결과를 밀어내는 것 방지). 하한은 평가 세트로 결정.
- 문서 의미 점수 = **최고 본문 청크 유사도 우선**, 본문 청크가 아직 없는 문서는 카드 유사도로 대체. M0: 카드·청크 단순 평균은 청크 단독보다 나쁨(특히 일상 표현 질의) → 결합 방식(가중치·최댓값)은 M2에서 비교. M2 비교 후보: 최고 청크(없으면 카드) · max(카드, 청크) · 카드·청크를 각각 RRF 목록으로 · 카드만.
- 결합·보정의 모든 값(k, 경로·필드·bigram 가중치, 하한, 가산 세기)은 실험과 제품이 함께 쓰는 검색 코어(`index::hybrid`)의 매개변수이고, 조정용 질의로 고르고 검증용 질의로 판정한다(M2 설계 §6, DEC-051).
- 보정: 정확 구절 일치 가산, 최근 문서 약한 가산, 날짜 칩 기간 가산.
- 재순위 모델은 1차 제외.

### 8.4 버전 묶기 (1단계에서 계산)
- 파일명 정규화: `최종`, `최최종`, `수정(본)`, `확정`, `(안)`, `vN`, `(N)`, `- 복사본`, `final`, 날짜(`yyyymmdd`, `yymmdd`) 제거.
- 규칙(우선순위 순):
  1. 정규화 이름이 다르면 묶지 않는다.
  2. 내용 해시가 같으면 → 같은 파일(중복, §6.4).
  3. 정규화 이름이 같고 **SimHash 유사도 ≥ 임계값**이면 묶는다. 같은 폴더면 임계값을 낮춘다. (초기값: 같은 폴더 0.7, 다른 폴더 0.85 — 평가 데이터로 조정)
  4. 이름만 같고 내용이 다르면 묶지 않는다.
- 임베딩을 쓰지 않으므로 1단계 직후부터 정확하며, 모델 교체의 영향이 없다.
- 대표는 최신 수정본.

### 8.5 필터 · 정렬
- 기본 칩: 📅 날짜(검색어 인식), 형식, 기간, 🛡 개인정보.
- `필터 더보기` 칩: 공문 시행일, 수신처/발신 기관, 폴더, 🔒 DRM.
- 정렬: 관련도(기본) / 최신순 — 목록 오른쪽 위 전환.

### 8.6 단계적 결과 전달
- 파일명(즉시) → 키워드(입력 멈춤 150ms) → 의미(임베딩 완료). 화면 동작은 UI D2를 따른다.

### 10.1 모델 관리
- 기본: **EmbeddingGemma 2** 텍스트 전용 GGUF **Q8_0**을 설치파일에 포함(M0 결정).
- **모델 프로필**(TOML): 이름, 파일 해시, 원본 차원, 저장 차원, 최대 토큰, 검색어/문서 접두어 템플릿, 풀링 방식, 정규화 여부. 알려진 모델 몇 개 내장, 미지 모델은 고급 설정에서 수동 입력.
- **모델 지문** = 파일 해시 + 프로필 해시. 벡터 디렉터리 이름 → 서로 다른 모델의 벡터를 섞지 않음. 벡터 폴더는 여기에 카드 상한·청크 설정을 더한 **임베딩 지문**을 쓴다 — 설정이 바뀌어도 옛 벡터를 섞지 않는다(DEC-047).

## 12. 개발 환경 · 테스트 전략

### 12.1 개발 환경
- macOS에서 `platform`(스텁 사용)·`svc`를 제외한 전 크레이트 개발·테스트.

### 12.2 3단계 검증
1. **GitHub Actions (windows 러너, 자동)**: 빌드, 단위·통합 테스트(USN·DPAPI·EFS·서비스·파이프 보안·MSI 설치/제거), E2E(tauri-driver), `cargo-deny`, 릴리즈 산출물 + SHA-256.
2. **사내 폐쇄망 PC (사용자 수행)**: 마일스톤 단위 릴리즈 반입 → `kra-search.exe --diagnose` → 보고서 반출.
   - 보고서: 환경(OS 빌드, CPU 명령어, RAM, EFS 가능 여부, WebView2 버전, 단축키 충돌, 감지된 백신, 네트워크 시도 점검), 합성 문서 벤치마크(초당 토큰, 검색 지연), 실제 문서 추출 통계(형식별 성공/실패/DRM/글자 없음/시간 초과, PDF 쪽 품질, 카드 길이 — m1-diag 부터), 정제된 로그.
   - **문서 본문·파일 경로·개인정보 미포함.** 경로는 확장자+해시만. 사람이 읽을 수 있는 JSON/텍스트. 맨 위에 옮겨 적을 수 있는 요약 몇 줄.
3. **폐쇄망 내 품질 평가**: 사용자가 `질의<TAB>정답 파일명` TSV 20~50개 작성 → `--eval queries.tsv` → nDCG@10, Recall@20, 실패 질의 번호만 출력.

### 12.3 테스트 종류
- 단위: 형식별 추출 샘플(배포용·암호·손상 HWP, ToUnicode 없는 PDF 포함), 개인정보 탐지(합성 번호만, 2020-10 이후 형식 포함), 버전 정규화·SimHash 묶기, 날짜 해석(기준 시점 고정 — 연말·연초·윤년 경계 포함), 검색어 유형 분류, 가중 RRF, bigram 토크나이저, 순서 변경 상태 기계.
- **공개 평가 세트(M0에서 구축)**: 공개 공공 문서(보도자료, 규정집, 정보공개 원문, 마사회 공개 자료) + 질의 ~100개 + 정답 → nDCG@10, Recall@20. 양자화·차원·청크 크기·bigram 가중치·RRF k·유사도 하한 결정 근거.
- 모델 정합성: GGUF vs 원본 출력 코사인(M0).
- 견고성: `cargo-fuzz`로 HWP/HWPX/PDF 추출기 퍼징. 워커 비정상 종료·시간 초과 시 앱 생존·워커 자동 재시작 확인.
- 성능: §13 기준을 벤치마크로 자동 측정(`--diagnose`에 포함).
- 네트워크 0: M7 패킷 캡처.

## 16. 로드맵

**2차**
- LLM 요약·질의응답 ("문서 도우미" 창, llama.cpp + 사용자 선택 GGUF, RAM 제한 없이 안내만)
- 붙임 파일 연결 (실제 문서로 정확도 측정 후 "관련 파일 후보"로)
- 네트워크 경로 (사용자 추가 시 주기 검사)
- 이미지·스캔 PDF 검색 (EmbeddingGemma 2 이미지 인코더 + OCR, 선택 기능)
- 이름·주소 개인정보 탐지 (NER)
- 재순위 모델 (고사양 PC 선택 기능)
- **부서 신호 활용** (2026-10-13 사용자 제안, 실험 후 결정): 부서를 입력받지 않고 공문 생산 부서(문서번호 "윤리경영부-3659")와 내 문서에서 가장 많이 나오는 부서로 **추정**한다.
  - 후보: ① 생산 부서 필터, ② 부서별 약어 사전, ③ 점수가 비슷할 때만 내 부서 문서를 약간 우선.
  - 하지 않을 것: 검색어 임베딩에 부서명 붙이기(모델이 그런 입력을 학습하지 않음), 내 부서 문서에 큰 가산점(다른 부서 규정을 찾는 검색을 방해).
  - 공문 구조 추출(**M4** — 생산 부서는 문서번호에서 읽으므로 공문 구조가 먼저 필요. 2026-10-15 M2 설계에서 옮김) 단계에서 마사회 문서를 늘린 평가 세트로 효과를 비교한 뒤 채택 여부를 정한다.
- **실사용 피드백 수집** (2026-10-13): 정말 유용한 업무 문서는 반출되지 않으므로 품질 개선은 실사용 피드백에 기댈 수밖에 없다. 1차 시범 운영 전에 최소 형태를 검토한다.
  - 앱 안 "원하는 문서가 안 나옴 / 순서가 이상함" 표시 → 로컬에만 기록(문서 내용·경로 없이 질의 유형, 정답 문서의 순위, 단계별 시간 같은 신호).
  - 반출용 피드백 보고서: 진단 보고서(§12.2)와 같은 원칙. 검색어 원문은 사람 이름이 들어갈 수 있어 **기본 제외**, 사용자가 화면에서 확인하고 고른 것만 포함.

**추후 검토**
- 옛 Office 형식 (.doc/.xls/.ppt — .xls는 calamine으로 저비용)
- 한셀(.cell)·한쇼(.show)
- 문서중앙화 연동, Fasoo SDK 연동(복호화 플러그인 인터페이스 활용)
- KCMVP 검증 암호모듈(ARIA) 옵션 — 요구 기관 발생 시
- 다중 사용자 PC에서 세션 간 색인 작업 조정
- 내장 GPU 가속 (llama.cpp Vulkan)
- 대규모 색인 시 HNSW
- "결과를 한 번에 표시" 옵션

**기타 아이디어** (보관만 한다. 실사용 피드백에서 필요가 보이면 꺼내 검토)
- **생산 기관별 결과 섹션** (2026-10-13 사용자 제안): 결과를 "한국마사회 / 농림축산식품부 / … / 기관 미상"처럼 생산 기관별 섹션으로 나눠, 같은 주제의 외부 문서(정부 보도자료 등)에 내부 문서가 밀리는 실패를 줄인다.
  - 보관 이유: 실제 업무 검색은 대부분 내부 문서 대상이라 외부 문서와의 경쟁이 평가만큼 크지 않을 수 있음(사용자 판단). 써 보면서 필요하면 꺼낸다.
  - 평가 근거: 마사회 섹션으로 나누면 정답 3위 안 64 → 72/72(Q8). 단 섹션이 문서 8건뿐이라 과대평가(results.md 발견 10, eval-dev.md §6).
  - 기관 판별 시험(1,005건, 시험 스크립트만): 외부 문서는 "○○부(장관 …)는"·제목 앞 기관명·머리 줄 기관명 규칙으로 약 2/3 를 높은 정확도로 판별. 최빈 기관명 추정은 절반쯤 틀려 쓰지 말 것. 로고가 그림뿐인 문서(약 7%)는 판별 불가. 별칭·조직 개편을 위해 정부·공공기관 이름 사전 필요(앱 업데이트로 갱신).
  - 내부 문서는 자기 기관명을 거의 안 씀(8건 중 0건 판별) → 공문 갑지의 발신 명의·문서번호, 부서명→기관 대응, 같은 폴더 연결, 자기 지칭("본회·우리회")으로 판별. 사용자 기관은 PC 의 갑지에서 가장 많은 발신 기관으로 자동 판별(입력 불필요).

- **업무 고유 시간 표현** (2026-10-15 M2 설계): 경마 "N주차·N회차·시즌" 같은 말이 공문에서 기간을 뜻할 수 있다.
  - 보관 이유: 경마 일정표 없이는 날짜로 바꿀 수 없고, 실제로 어떤 표현을 쓰는지 아직 모름(사용자 판단 — 써 보면서 피드백으로).
  - 넣는 자리: 날짜 표현 표는 바깥 파일을 덧붙일 수 있게 만들었다(§8.1). 표현과 해석 규칙(필요하면 일정표)을 더하면 된다.

- **본문·파일 속성에서 문서 시기 추정** (2026-10-15 M2, 사용자 승인): 수정일·제목 연도 외에 본문 날짜나 HWP/DOCX 속성의 작성일로 "언제 쓴 문서인지"를 추정한다 — 내용 시기 질의(작년 매출액)의 순위 하락(KI-049) 대책 후보.
  - 보관 이유: 본문 날짜는 관련 근거·계획 일정 날짜가 섞여 위험하고, 양식을 복사해 쓰면 속성 작성일이 옛 날짜로 오염된다.
  - 꺼낼 때: M4 공문 구조(시행일) 작업 때 시행일·본문 날짜·속성 날짜를 함께 비교한다. 폐쇄망 확인의 날짜 질의 실패 수로 영향을 본다.

- **사용자별 검색 습관 맞춤** (2026-10-15 M2, 사용자): 검색어 유형(키워드형/의미형) 비중을 사람마다 다르게 둔다.
  - 보관 이유: 사람마다 검색 습관이 달라 하나의 유형 기준이 맞지 않는다 — 그래서 지금은 나누지 않는다(DEC-058·DEC-064). 실사용 피드백(앞의 2차 항목)이 쌓이면 개인별 비중을 검토한다.
