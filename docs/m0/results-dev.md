## 2. 검색 품질 비교 (Task 10) — 상세 표: [eval-dev.md](eval-dev.md)

말뭉치: 공개 보도자료 1,000건(추출 997, 암호 문서 3) · 질의 130개(semantic 40, keyword 30, abbrev 15, temporal 15, deep 30) · **의미 검색 단독**(키워드 검색 없음) · Apple M4 Pro.

> 1차(문서 200건)는 모든 설정이 nDCG@10 ≥ 0.98로 천장 효과가 나서, 비슷한 주제의 문서 800건과 본문 깊은 곳을 묻는 `deep` 질의 30개를 추가해 다시 쟀다.

| 비교 | 결과(nDCG@10) | 해석 |
|---|---|---|
| **점수 방식** | 본문 청크 0.959~0.974 > 카드+청크 평균 0.923~0.955 > 카드만 0.856~0.889 | 문서 카드만으로는 부족(특히 `deep` 0.63~0.72 vs 청크 0.89~0.94). **2단계 구조(빠른 카드 → 정밀 청크)의 근거.** 단순 평균 결합은 청크 단독보다 나쁨 → 결합 가중치는 M2에서 조정 |
| **Q8 vs Q4** (768, 청크 400) | 0.9660 vs 0.9641 (차이 0.2%p) | 1%p 이내 → 규칙상 **Q4** |
| **차원** (Q8, 청크 500) | 768 0.9742 · 512 0.9733 · 256 0.9640 | 512는 0.1%p, 256은 1.0%p 하락 → **512** |
| **청크 크기** (Q8, 768) | 300 0.9732 · 400 0.9660 · 500 0.9742 | 크기와 무관하게 오르내림 → 잡음 수준(±0.5%p). 규칙상 작은 쪽 **300**(긴 문서가 적은 말뭉치의 한계 — README 참고) |

## 3. 이진 후보 선별 재현율 (Task 10)

본문 청크 13,338개, 기준은 int8 256차원 완전 스캔 상위 10.

| 방식 | 후보 1% | 후보 2% | 후보 5% |
|---|---|---|---|
| 해밍 256비트 | 0.875 | 0.925 | **0.956** |
| 비대칭 256비트 | **0.956** | 0.978 | 0.995 |
| 해밍 768비트 | 0.938 | **0.968** | 0.983 |
| 비대칭 768비트 | 0.976 | 0.986 | 0.993 |

- 95%를 넘는 가장 싼 조합: **해밍 256비트 + 후보 5%** 또는 **해밍 768비트 + 후보 2%**. 비대칭 점수는 재현율이 좋지만 50만 개 스캔이 해밍보다 수십 배 느리다(M4 Pro: 76ms vs 2ms) → 저사양 PC 실측 후 결정.
- 스펙의 "후보 1,000개 고정"은 규모가 커지면 비율이 너무 작아진다 → **후보 = max(1,000, N × 비율)**로 바꿀 것.

## 5. Windows 빌드 성능 사고와 수정 (Task 12)

- `cmake` 크레이트가 MSVC Release 옵션을 덮어써 llama.cpp가 **최적화 없이** 빌드되었다(Q4 2스레드 29토큰/초).
- 옵션을 직접 지정해 수정(/O2) → 같은 CI 서버 2코어에서 **Q4 380 · Q8 233토큰/초**(m0-diag-3). clang 빌드는 약 5% 빠를 뿐이라 MSVC 유지.
- 재발 방지: 최적화 옵션이 빠지면 `llama-sys` 빌드가 실패한다.
