## 2. 의미 검색만으로 못 찾던 질의(results.md 발견 7) — 키워드 순위
| 질의 | 의미(M0) | 키워드(M1) |
|---|---|---|
| D012 변화관리협의체 고위험 모니터링단 | 22~23위 | 14위 |
| D028 손해배상 책임보험금 상향 금액 | 64~85위 | 12위 |

## 3. 해석
- 키워드 단독은 거의 모든 유형에서 의미 검색보다 낮다(전체 0.7946 대 0.9122). 낱말이 질의와 문서에 겹치는 abbrev(1.0000)·temporal(0.9850, 의미 0.9695보다 높음)·keyword(0.9553)에서만 대등하다.
- 가장 크게 뒤지는 유형은 kra-plain(0.2068 대 0.6202, Recall@20 0.4386)이다. 일상 표현 질의에는 문서와 겹치는 낱말이 거의 없어 키워드가 약하다. P003·P008 은 100위 안에도 못 든다. 이 간격을 의미 검색이 메운다.
- 의미 검색이 못 찾던 D012(22~23위 → 14위)·D028(64~85위 → 12위)은 키워드에서 순위가 올랐지만 둘 다 여전히 10위 밖이다. 결합(M2)에서 두 신호를 합치면 10위 안으로 들어올 여지가 있다. 이 기대는 M2 에서 확인한다.
- M2 기대: 키워드의 강점(고유명사·약칭·시점 낱말)과 의미의 강점(바꿔 말한 질의)이 다른 곳에 있어, 하이브리드가 두 단독 점수보다 높아야 한다.

비교 조건의 차이(숫자를 읽을 때 감안):
- 추출이 M0 와 다르다 — M1 은 HWP 캡션(KI-015)·HWPML 판별(KI-010)이 더해져 글자가 조금 늘었다. 의미 검색 열은 M0 추출로 잰 값이다(M2 에서 같은 추출로 다시 잰다).
- 평가 문서는 매니페스트 제목이 **문서 제목(3.0)과 파일명(2.5) 필드 둘 다**에 들어간다. 실제 PC 의 파일 이름은 제목과 다른 경우가 많아, 이 키워드 점수는 실제보다 유리하게 나온다.
- 문서 1,004건을 읽었다(M0 는 1,005건). 새로 추출이 실패한 문서는 P0833(138MB HWPX, 크기 상한 `TooLarge`) 1건이며, 어떤 질의의 정답에도 없어 점수에는 영향이 없다. 암호 문서 3건(P0126·P0404·P0702)은 M0 와 같다.
- 속도(이 PC): 색인 약 1.3초(문서 1,004건, eval-keyword.md 생성 보고서 값) · 검색 p50 0.1ms / p95 0.2ms.
- 이 절의 1,004건은 평가 말뭉치 전체(공개 세트 + 마사회 평가 문서)에서 **내용을 읽은 문서 수**다. §4 의 1,000개(읽음 996 · 못 읽음 4)는 **공개 세트 폴더 하나**를 `kra-search index` 로 색인한 파일 수라 집계 대상이 다르다.

## 4. 개발 PC 색인 속도

개발 PC(Mac, Apple Silicon), 릴리즈 빌드, `--home /tmp/kra-home`(임시 폴더, 측정 뒤 삭제). 명령은 CLAUDE.md "개발 명령"의 `kra-search index` / `search`.
메모리는 M1 최종 수정(2026-10-15) 뒤 앱과 워커를 **따로** 다시 쟀다 — `ps` 로 20ms 마다 앱 프로세스와 그 자식(워커)의 RSS 를 표본으로 잡은 최대값(짧은 최대값은 놓칠 수 있음). `/usr/bin/time -l` 의 값은 앱과 기다린 자식이 섞여 원인을 나눌 수 없다.

| 항목 | 값 |
|---|---|
| 공개 평가 세트 문서 수 | 1,000개 — 내용을 읽은 것 996, 못 읽은 것 4 |
| 색인 시간(전체, 처음부터) | 실행 파일만 4.7초(`/usr/bin/time`). 처음 적은 6.8초는 `cargo run` 의 빌드 확인·시작 시간이 들어간 값. 최종 수정(워커 재활용 23회) 뒤 5.0초 |
| 검색 시간(명령 전체, 사전 로드 포함) | 고령친화도시 0.05초 · 일자리 전담반 0.06초 · 렛츠런파크 0.06초 · 산림항공 0.05초 |
| 키워드 색인 크기 | 7.9MB |
| meta.db 크기 | 12MB |
| 색인 최대 메모리 — 공개 세트 1,000개(최종 수정 뒤) | 앱 약 140MB · 워커 약 180~240MB(두 번 측정) · 동시 합 약 300~360MB. `/usr/bin/time -l` 314MB |
| 색인 최대 메모리 — 공개 세트 1,000개(최종 수정 전) | 앱 약 136MB · 워커 약 490MB(상주 워커 누적). `/usr/bin/time -l` 508MB(507,805,696바이트) |
| 색인 최대 메모리 — 90MB 한국어 TXT 1개(최종 수정 뒤) | 앱 약 196MB · 워커 약 190MB, meta.db 12MB. 최종 리뷰 실측(수정 전) 앱 약 743MB · 워커 약 580MB · meta.db +97MB |
| 색인 최대 메모리 — 500만 자 문서 1개(`big.txt`, 문단 36만 개) | 약 239MB(238,731,264바이트), 색인 2.1MB·meta.db 23MB, 2.1초 |

해석
- 검색 지연 기준 p95 ≤ 150ms 는 상주 앱 기준이다. 명령줄 실행은 형태소 사전 로드 시간이 매번 더해진 값이다(그래도 0.05~0.06초).
- 큰 문서 하나의 최대 메모리 239MB 는 DEC-041 의 리뷰 실측(한 값으로 넣을 때 약 1.2GB)보다 크게 작고 기준 300MB 안이다. 앱 전체(사전 약 43MB 포함)이므로 키워드 색인만의 140MB 보다 크다.
- (정정) 처음 적은 "공개 세트 1,000개의 최대 메모리 508MB 는 색인 쓰기 버퍼·meta 쓰기·사전·워커 응답이 겹친 값"은 틀렸다. 앱과 워커를 따로 재 보니 앱은 약 136MB 였고 508MB 는 **상주 워커가 쌓은 메모리**였다 — 그림이 많은 10~48MB HWPX 하나마다 워커가 파일 크기의 약 3배씩 늘고 돌려주지 않았다(문서 하나만 읽으면 최대 158MB). 최종 수정에서 워커를 읽은 크기 64MB 마다 새로 띄워(DEC-033 (2)) 워커 최대를 약 180~240MB 로 낮췄다. 남은 부분은 KI-037.
- m1-diag 는 파일마다 새 자식 프로세스로 추출하므로 이 누적을 보지 못한다. 저사양 PC(RAM 8GB 이하)에서 색인 중 메모리는 M5 상주 앱에서 Windows 로 다시 잰다(KI-037).
- 못 읽은 4개는 위 §3 의 암호 문서 3건(P0126·P0404·P0702)과 크기 상한을 넘은 P0833 으로 보이며(파일명만 색인), 실패 종류별 확인은 m1-diag 결과로 한다.

### 5.5 M2 계획에 넘길 것 (권고 — M2 계획에서 확정)
1. **임베딩 스레드 기본값 4**(성능 코어 수보다 크지 않게), 논리 스레드 수는 절대 쓰지 않는다 — 최고 속도의 97% 를 내면서 사용자 작업에 코어를 남긴다(KI-017).
2. **본문 임베딩은 문서 형식부터**(hwp·hwpx·pdf·docx·pptx·odt·odp), 데이터 형식(txt·csv·xlsx·ods)은 키워드만 하거나 문서당 앞 몇 청크로 제한 — 데이터 형식이 본문 토큰의 68% 이고 너무 긴 문서도 대부분 데이터 형식이다. 문서 형식만이면 이 PC 에서 Q8 약 3시간(주 기준 PC 는 더 길다).
3. **카드 30분 기준 미달**(KI-041) → **결정 #27(사용자, 2026-10-15)**: 품질이 우선. 카드는 최근 수정 문서·문서 형식부터 만들고(기본), 상한 128토큰은 M2 평가에서 256 보다 조금이라도 유의미하게 떨어지면 쓰지 않는다(기준은 스펙 §18 #27). M0 의 "128 효과 없음"은 평가 카드(평균 64)로 낸 결과라 실제 카드(평균 123)에는 근거가 되지 못한다 — 평가 세트에서 128 로 잘리는 카드가 적으면 판단 불가로 보고 256 을 유지한다.
4. **날짜 가산은 수정일로 진행**(스펙대로) — 분포가 고르게 퍼져 있다.
