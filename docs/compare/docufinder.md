# Docufinder(Anything)와 비교 평가

- 날짜: 2026-11-02 · 계기: 비슷한 공개 프로그램 발견(사용자). "계속할 강점이 있나"를 숫자로 확인.
- 대상: [chrisryugj/Docufinder](https://github.com/chrisryugj/Docufinder) v3.8.14(b9f57f7, 2026-10-20 릴리즈) — Tauri 2 + Rust, SQLite FTS5 + lindera, KoSimCSE int8(ONNX, 128토큰) + usearch, RRF(k=60), HWP/HWPX 는 번들 kordoc(Node). 라이선스 **BSL 1.1**(비프로덕션만 무료, 2030-04-15 Apache-2.0 전환).
- 우리: m2 브랜치 fd0d045 제품 경로(`kra-search eval --set … --dump`), 기준 시점 2026-10-15 = M2 결과와 같은 순위(일치 확인).
- 채점표 전체: [docufinder-eval.md](docufinder-eval.md) · 하네스·재현: `tools/compare/docufinder/`

## 1. 조건

- 평가 세트: M2 와 같은 문서 1,062건 · 질의 255개(public · kra · data), 같은 조정용/검증용 분할(DEC-051), 같은 지표 함수(`app::evalset`). 두 프로그램 모두 **같은 복사본 폴더**(파일 이름·수정일 = 매니페스트, DEC-052)를 색인했다.
- Docufinder 는 화면 기본값 그대로: 결과 50개, 키워드 AND, 버전 접기 켬. 하네스는 '폴더 추가'와 같은 순서로 색인하고 화면 명령과 같은 서비스 함수를 부른다. 청크 결과는 파일 첫 등장 순서로 줄였다(화면도 파일 한 줄).
- Docufinder 세 모드:
  - **하이브리드**: 설정에서 의미 검색을 켠 상태의 기본 검색. 비교의 주 대상이다.
  - **스마트**: 자연어 모드로, 날짜·형식 조건을 읽어 거른다.
  - **키워드**: 의미 검색이 꺼진 기본 상태이며, 내부망 Lite 판에서는 이것만 있다.
- 개발 PC(Apple Silicon)에서 쟀다. 우리 숫자는 M2 결과와 같다(8스레드로 색인).

## 2. 결과

| 실행 | 매크로 nDCG@10 검증용 | 첫 페이지(전체) | 첫 페이지(검증) | Recall@20 | 결과 없음 |
|---|---|---|---|---|---|
| **우리 하이브리드** | **0.7803** | **248/255 (97.3%)** | **97/100** | **0.9716** | 0 |
| 우리 키워드(모델 없는 제품 경로) | 0.6927 | 228/255 (89.4%) | 91/100 | 0.9182 | 0 |
| Docufinder 하이브리드 | 0.6322 | 215/255 (84.3%) | 81/100 | 0.8361 | 16 |
| Docufinder 스마트 | 0.5557 | 198/255 (77.6%) | 76/100 | 0.7777 | 27 |
| Docufinder 키워드(Lite 판) | 0.3589 | 95/255 (37.3%) | 38/100 | 0.3550 | 148 |

합성 데이터 세트를 빼고(질의 243) 같은 일을 하는 부분만 비교해도 순서는 같다. 검증용 매크로는 우리 0.9008, Docufinder 하이브리드 0.7727이고, 첫 페이지는 240/243과 213/243이다(채점표 B).

질의별 첫 정답 순위(우리 하이브리드 대 Docufinder 하이브리드)는 우리가 앞선 질의 70개, 같은 질의 159개, 뒤진 질의 26개다.
- 첫 페이지 기준으로 보면 우리만 첫 페이지에 넣은 질의가 34개다. 유형별로 semantic 7, date 7, kra-plain 6, kra-deep 6, data 6, 그 밖 2개.
- Docufinder만 첫 페이지에 넣은 질의는 P012(kra-plain) 1개다. 우리는 23위, Docufinder는 4위였다.

## 3. 해석

1. **의미 검색을 켜면 Docufinder 도 강하다. 그래도 차이는 분명하다.**
   - 유형별로 keyword(Docufinder 0.968 · 우리 0.987)·abbrev 는 비슷하고, temporal 은 Docufinder 가 높다(0.937 · 0.889).
   - 차이는 다른 유형에서 난다. semantic 0.76 대 0.98, kra-deep 0.68 대 0.79, date 0.68 대 1.00, 데이터 형식에서 크게 갈린다.
   - 의미 질의에서 결과가 아예 없는 경우도 있다(semantic 5개). 키워드가 맞지 않으면 유사도 0.5 미만의 벡터 결과를 버리기 때문이다(`VECTOR_ONLY_MIN_SCORE`).
2. **폐쇄망 판(Lite)은 비교가 되지 않는다.**
   - 키워드 AND라서 질의 255개 중 148개(58%)가 결과 없음이다.
   - 마사회 망분리 PC에서 보안 심사로 Lite 판을 쓰게 되면, 우리 모델 없는 경로(0.69)보다도 훨씬 낮다.
3. **날짜 질의는 우리 고유 기능이다.**
   - Docufinder 하이브리드는 날짜 표현을 읽지 않는다(date 0.68).
   - 스마트 모드는 날짜를 읽지만 실제 오늘(2026-11-02)을 기준으로 거른다. 평가 기준 시점(2026-10-15)과 달라 "지난달·이번 주" 질의가 불리하다. 그래서 스마트의 date·temporal 숫자는 판정에 쓰지 않는다. 하네스는 그쪽 시계를 바꾸지 않는다.
4. **데이터 형식은 지원 범위 차이다.**
   - Docufinder는 `.csv` 를 색인하지 않는다(16건, 정답 질의 5개). 그래서 data 유형 차이의 일부는 구조적이다.
   - xlsx·txt 질의에서도 첫 페이지는 우리 6/7, Docufinder 2/7이다(csv 질의는 2/5 · 0/5). 다만 질의 수가 적다.
5. **편향 주의.**
   - 평가 세트는 우리가 우리 요구(마사회 문서, 날짜 표현, 일상 표현)에 맞춰 만들었다.
   - 우리 매개변수는 조정용 질의로 골랐다. 그래서 검증용 숫자를 주로 본다.
   - Docufinder의 자체 벤치(정보공개 결재문서 50건·질의 44개, 벡터 단독)는 이것과 직접 비교할 수 없다.

## 4. 우리가 뒤지는 점(숨기지 않음)

- **색인 속도.** 같은 Mac에서 Docufinder는 6분 남짓, 우리는 약 62분이다(M2 results §3.2).

  | 단계 | Docufinder | 우리 |
  |---|---|---|
  | 키워드 색인 | 12.5초 | 5.8초 |
  | 벡터 색인 | 305초(청크 12,126, 평균 약 3코어) | 3,704초(카드 1,058 + 청크·데이터 뒷부분 22,473, 8스레드) |

  - KoSimCSE(128토큰)는 EmbeddingGemma 2보다 훨씬 가볍다. 우리도 첫 결과는 카드 단계(30.5초)에서 나오지만, 정밀 단계의 체감 문제(KI-041, 결정 #27)가 비교로 더 분명해졌다.
- **메모리.** Docufinder 하네스(색인 + 검색)의 최대 상주 메모리는 1.34GB다. 우리는 같은 조건으로 재지 않았다.
- **기능 폭.** Docufinder에는 OCR, 미리보기·원본 레이아웃, 문서 비교, `.eml`, 파일명 검색, AI 질의응답, DRM 대안 경로(MS Office로 읽기)가 있다. 우리는 아직 화면이 없다(M3).
- 추출 실패는 둘 다 같은 4건이다(암호 HWPX 3건, 큰 그림이 든 HWPX 1건).

## 5. 결론

- 우리 평가 세트에서 우리 하이브리드는 Docufinder 최고 설정(의미 검색 켬)보다 검증용 nDCG@10이 +0.15 높다. 첫 페이지 적중도 97%로 81%보다 높다. 사용자 원칙인 "첫 페이지에 정답"으로 보면 질의 34개 대 1개 차이다.
- 강점은 세 가지다. 의미 질의, 마사회 문서, 날짜 표현.
- 폐쇄망(Lite)에서는 차이가 더 벌어진다. 라이선스(BSL)까지 생각하면 마사회가 그대로 쓰기 어렵다.
- 반대로 색인 속도와 기능 폭은 뒤진다. 이 비교에서 나온 아이디어는 스펙 §16 '기타 아이디어'에 보관했다.
